30分で終わる話でも、1時間の会議を設定すると、なぜか1時間かかります。

「では会議を短くするには？」とAIに聞けば、議題を明確にする、参加者を絞る、時間を守る、といった対策を挙げてくれるでしょう。

間違ってはいません。でも、**正しいことが並んでいるのに、読み終えてもあまり印象に残らない**。そんな説明に出会うことがあります。

一方、同じ問いをこう考えると、景色が変わります。

> 30分で終わる話でも、1時間の会議を設定すると、だいたい1時間かかります。
>
> 話すことがあるから時間を使うのか。それとも、時間があるから話すことを作るのか。
>
> 会議の価値を「話した時間」で測れば、1時間の会議は立派です。しかし「何が決まったか」で測れば、10分の会議に負けることもあります。
>
> 仕事を進めるための会議が、会議をするための仕事になってしまうわけです。

これはこの記事のために書いた**説明の作例**です。上岡龍太郎氏の実際の発言ではありません。

言っていることは難しくありません。むしろ、使っている言葉は簡単です。

それでも印象が変わるのは、**答えを並べるのではなく、読み手が納得する順番で話を進めているから**ではないでしょうか。

この「説明の組み立て方」をAIエージェントのスキルにしてみました。

**[Kamioka Logical Explainer（GitHub）](https://github.com/tamutamu/kamioka-logical-explainer)**

## 「上岡龍太郎風の口調」にしたかったわけではない

上岡龍太郎氏の説明が印象に残る理由を考えるとき、最初は「話がうまい」「語彙が豊富」「頭の回転が速い」といった感想が浮かびます。

でも、それではAIに指示できません。

「もっと頭のいい説明をして」「上岡龍太郎風に話して」と頼んでも、何をどう変えればよいのかが曖昧だからです。

欲しかったのは口調ではなく、**話を聞く人の頭の中で、納得が生まれるまでの道筋**でした。

そこで、説明を5つの動きに分けました。

## 説明のうまさを、5つの動きに分ける

| 動き | 何をするか | 会議の例 |
| --- | --- | --- |
| ① 身近な場面から入る | 読み手がすぐ想像できる状況を示す | 30分の話に1時間の枠を取る |
| ② 建前を問い直す | 当たり前だと思っていた前提を疑う | 話が多いから長いのか？ |
| ③ 判断の物差しを置く | 何をもって良いとするか決める | 話した時間より、決まったこと |
| ④ 背後の仕組みに進む | 一つの例から共通する構造を見つける | 時間の枠が話題を増やすこともある |
| ⑤ 逆説で締める | 説教ではなく、気づきを残す | 会議をすることが仕事になる |

ここで大切なのは、5項目を見出しにして機械的に埋めることではありません。

**読み手には、一つの自然な話として届くこと。** スキルでは、この5段階を内部の組み立て方として使い、文章には原則としてステップ名を出さないようにしています。

### いちばん大事なのは「物差し」

私が特に重要だと考えたのは、③の判断基準です。

例えば「なぜ学歴は今も重要なのか」と聞かれたとします。

「学歴より実力だ」という話と、「学歴は採用に役立つ」という話は、対立しているように見えます。

でも、「本人の能力がすでに分かっているのか」という物差しを入れると、整理できます。

採用前なら、学歴は能力を推測するための材料の一つです。仕事ぶりを何年も見たあとなら、実績という直接的な材料があります。

**学歴が役に立つ場面と、学歴に頼る必要が薄くなる場面は違う。**

結論だけ言うより、この違いを先に示したほうが、読み手は自分の頭で判断できます。

## 単なる「それっぽい文章」にしないために

この種のスキルには落とし穴もあります。

文章が滑らかで、最後の一文が鮮やかだと、根拠まで正しいように感じてしまうことです。

そこで [SKILL.md](https://github.com/tamutamu/kamioka-logical-explainer/blob/main/SKILL.md) には、話し方だけでなく、次の制約も入れています。

- **事実と推測を混ぜない。** 数字や引用を作らず、確認できない例は仮定だと明示する。
- **一つの例から決めつけない。** 「人は必ず」「企業はすべて」と飛躍しない。
- **例えの対応をそろえる。** 面白い例えでも、論理がずれるなら使わない。
- **相手を言い負かさない。** 目的は論破ではなく、理解です。

「誰もが納得する説明」を目指すとしても、反論できないような錯覚を作りたいわけではありません。

**筋が通って聞こえることと、本当に筋が通っていることは別**だからです。

## 使ってみる

Agent Skillsに対応する環境で、次のコマンドから追加できます。

```bash
npx skills add tamutamu/kamioka-logical-explainer
```

[Skills CLI](https://github.com/vercel-labs/skills) を使わない場合は、リポジトリ直下の `SKILL.md` を対応するエージェントのスキルとして配置する方法もあります。

あとは、たとえばこう依頼します。

```text
Kamioka Logical Explainer を使って、
「なぜ人はマウントを取るのか」を説明してください。
専門用語を避け、身近な一言から始めてください。
```

別の使い方もできます。

```text
以下の説明文を Kamioka Logical Explainer で書き直してください。
結論は変えず、具体例から入り、判断の物差しを明確にしてください。

（ここに文章を貼る）
```

「なぜ会議は長くなるのか」「なぜ今も学歴が重要なのか」のような問いだけでなく、提案文や技術解説の書き直しにも使えるように設計しています。

なお、今回示した文章はスキルの考え方を伝えるための作例であり、導入前後を測定した比較実験ではありません。出力の品質は使うモデルや題材にも左右されます。

## おわりに

AIは、求めればいくらでも言葉を増やしてくれます。

でも、わかりやすい説明に必要なのは、必ずしも言葉の多さではありません。

**最初に何を見せ、何を疑い、どの基準で考え、どこへ着地させるか。**

その順番を決めるだけで、同じ話がずいぶん違って聞こえます。

言葉を大量に作れるAIに、あえて**余計な言葉を使わずに説明する方法**を教える。

そこに、このスキルを作った面白さがあると思っています。
